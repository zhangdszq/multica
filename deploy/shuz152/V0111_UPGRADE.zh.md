# SHUZ-158：v0.11.1 升级技术设计

## 结论与审批范围

目标是官方稳定 tag **v0.11.1**，于 2026-11-19 发布，提交 `e1fe10d6694848e35dd1aa00e08cd11d93e545ac`。当前测试、正式环境仍运行 v0.8.2，应用提交 `f21f10733b06799bdf45526a0d4fc897dcb0af7f`，数据库最高迁移为 `642_migrate_fork_project_access`。

本批新增 **60 项数据库迁移，fork 编号 643–702**。工作区 AGENTS.md 要求测试环境表结构变更须经人工审批，正式环境数据库写入须有明确指令。上一批 616–642 的批准不覆盖本批。本文提交本批迁移、测试环境验证及通过后正式上线的审批；批准前只进行代码集成、无数据库写入的检查和备份。

本文件是升级设计，不能当作已经上线的验收记录。

## 目标与保留行为

- 合入官方 v0.8.2 到 v0.11.1 的代码及文档，目标固定在 tag，不跟随尚未发布的 main。
- 保留任务正文窄、正常、宽三档，默认正常；保留图片排列偏好及附件下载超时修复。
- 项目访问继续采用官方 `visibility`、`project_member`、`creator_type/id` 模型。旧定制字段仅为回滚保留，不恢复旧权限判定或双写。
- 642 已完成旧授权迁移；本批不再次执行桥接迁移，不重建或清空项目成员表。
- 官方新 `guest` 角色沿用官方边界；现有成员不自动改为 guest。项目订阅表只决定通知订阅，不授予项目访问权限。
- 当前两个部署均未设置 `MULTICA_CLOUD_URL`。官方 entitlement 客户端在该配置为空时不接入 Cloud，不限制私有项目的新增或既有读取；不添加 Cloud 配置。
- 本次服务器版本升级不会自动替换成员电脑已安装的 CLI，也不会重启成员运行端。

## 集成方式

从 fork `origin/main`（`08d9002d809e03005c9109757acc941cd5aca3e4`）建立升级分支，以 merge 保留官方历史。

1. 官方新增迁移 637–696 顺序映射到 fork 643–702；按完整迁移名称更新 runner、清理 hook 与测试引用。
2. 已有 **1,333 个迁移目录文件**逐字节保留，包括历史 SQL 和编译时 manifest。官方 v0.8.2 到 v0.11.1 没有修改早于本批的历史 SQL。
3. 重新生成 sqlc，使官方新增字段与 fork 保留的旧字段均正确扫描。
4. 界面冲突同时保留官方窗口菜单、布局间距与 Markdown 渲染缓存，以及 fork 宽度、图片排列设置。
5. Markdown 缓存键包含图片布局作用域，避免同一内容在任务和普通聊天之间复用错误的图片分组树。
6. 构建工作流读取当前版本号，避免候选服务仍报告旧的 0.8.2。

官方新版本保留每个收件人最新 2,000 条可见活跃通知，超出的旧通知自动归档，可以从已归档查看；不删除任务或评论。稍后提醒中的通知、不再有权限的项目通知不参与可见通知排序。

2026-11-19 只读预检：测试环境未归档通知最大 553 条；正式环境有 1 个收件人超过 2,000 条，最大 2,037 条。这是旧版未归档数的上界，尚未扣除无权访问的项目。实际归档量须按新版本权限与可见规则核对。验收应检查该成员的活跃、已归档列表及权限过滤。

## 批准后的验证和发布顺序

1. 候选 CI、静态检查通过后，先用受控副本演练从 642 到 702 的迁移及重复执行；测试版恢复验证和权限用例在该批表结构审批后进行。
2. 对比项目属性、授权集合，逐人验证原授权成员仍能访问私有项目，普通未授权成员不能访问。覆盖任务、附件、搜索、文档关联和智能体代执行。
3. 测试环境切换到固定提交的候选前后端镜像，只修改镜像引用，保持现有端口、网络、卷和私密配置；重启测试网关以更新容器地址。
4. 浏览器验收登录、项目权限、任务正文三档宽度、图片布局、附件上传下载、桌面窗口菜单兼容入口及移动宽度；验证新文档功能。保存截图到 PR。
5. 测试环境验收完成才合并 PR。正式切换前停写、重新备份与记录权限集合，执行同一批迁移，启动相同候选镜像，再核对健康、版本、权限和附件。
6. 观察错误日志和新任务执行。不重启生产 Nginx、数据库或用户运行端，不启动废弃旧 compose。

## 回滚机制

- 保留当前 v0.8.2 前后端镜像、完整私密容器配置、compose、上传卷及切换时备份。
- 测试演练要验证旧应用在扩展后的表结构上能否安全启动和通过旧 manifest 检查；验证前不能声称可以无损仅回滚镜像。
- 正式恢复写入前发现问题：保持停写，恢复切换时数据库快照与旧应用配置，核对快照校验值、健康和授权集合，再开放流量。
- 恢复写入后发现问题：先停写并另外备份当前状态，评估增量数据；优先使用已验证的旧镜像兼容回退。需要数据库恢复时须明确恢复点及增量补偿，不能静默丢弃上线后业务数据。
- 并发索引失败先检查 INVALID 索引与 runner hook，重试原迁移；不改历史 SQL 或手动将失败项标记成功。
